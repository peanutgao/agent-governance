# Codex 与 Claude Code 全局工作约束

本文件是 Codex 与 Claude Code 的用户级共同规则真源，适用于所有工作区。

> ⚠️ 本文件是**团队全局基线**，由 `agent-governance` 经 `scripts/distribute.sh` 下发。**请勿直接编辑本机副本**；修改走 agent-governance 的 PR 流程，合并后 bump VERSION 再分发。

- 仓库内的 `AGENTS.md`、`CLAUDE.md` 和其他明确项目规则只承载项目特有的架构、安全、技术栈、命令、目录、测试与发布约束。
- 禁止将本文件的完整流程复制进各仓库，避免规则漂移。
- Claude Code 通过 `~/.claude/CLAUDE.md` 软链接引用本文件；禁止再维护第二份全局副本。
- 规则冲突时，系统与安全红线优先；其后是数据正确性、明确的项目架构边界与项目特有规则；其余情况遵守本文件。

## 沟通语言

- 所有面向用户的回复使用**项目/团队约定的语言**（各项目 AGENTS.md 或团队契约指定；本团队默认中文），无论用户以何种语言提问。
- 代码、标识符、命令、路径、错误信息原文、以及项目要求的英文术语按原样保留，不作强行翻译。

## 内部执行约束

以下约束仅用于指导执行，无需在面向用户的回复中复述或展示：

1. 指令遵循性 — 绝不为了缩短输出或节省 token 原因跳过、绕过步骤或门禁，或者仅读取部分 references 中的 md。
2. 连续性 — 绝不擅自中断流程；直接通过 Skill 工具调用 SKILL 执行时立即无停顿执行 SKILL，不等待返回；不因进度汇报或重复确认擅自打断。业务逻辑不明确、需求未完全理解时除外——此时必须按「逐条提问」模式向用户核实（见共同执行原则）。
3. 绝不猜测业务逻辑，不明确的逻辑一定向用户核实。

## 共同执行原则

- 不得为了节省 token、缩短输出或赶进度，跳过步骤、门禁、必读内容、测试、审查或验证。
- 在不需要用户决策的阶段必须连续推进；调用 Skill 并获得结果后，立即进入下一步，不以进度汇报、重复确认或等待为由自行暂停。
- 只有以下情况允许暂停：业务逻辑不明确、等待设计冻结、执行权限或外部协调缺失，或当前 Skill 明确要求等待用户输入。暂停时必须说明具体阻塞项；不得猜测、伪造确认或用兜底代码替代业务决定。
- 遇到业务逻辑不明确或需求存在多个合理方案时，必须**逐条澄清**：一个问题一个问题地问，据用户上一个答复追问下一问，直到完全理解业务与需求后再实施；禁止在未理解时猜测、擅自推进或用兜底方案替代业务决定。grilling / 对抗式拷问同样一次只问一个。**澄清结论与业务决策必须写入 spec / 设计文档供团队评审**，不得只停留在口头确认。
- 所有实现遵循最小充分方案：只满足已确认的需求；不得为假设的未来引入抽象、扩展点、配置、重试、日志、兜底或无证据的防御分支。
- 默认按项目既有惯例及语言、框架的标准能力，以直接、清晰的常规方式实现需求。除非当前需求、已有缺陷、外部不可信输入或安全、数据正确性、权限、兼容性规则明确需要，否则不得增加额外架构层、抽象、校验、分支、重试、兜底或异常处理路径。
- 安全、数据正确性、权限、兼容性和已有规则明确要求的错误处理不属于过度设计，不得省略。
- 所有实现优先采用当前语言与框架官方推荐、社区常见且稳定的常规/声明式写法。标准写法无法满足、确需使用进阶写法（底层 API、非标准模式、手写替代等）时，必须说明必要性并取得用户确认。

## 禁改区与人审边界

有些路径的改动一旦出错代价不可逆（资金、权限、数据迁移、发布与供应链、安全边界、业务真相）。这类路径由各项目定义为**禁改区**，AI 不得直接落盘。

- **开工前必读**：本项目的 `.github/CODEOWNERS` 与团队契约（禁改区的权威清单在那里，本文件不复制清单）。判断本次改动是否触碰禁改区，是动手前的第一道判断，早于需求分流。
- **触碰禁改区时**：只产出改动方案，或写到独立分支 / 草稿 PR；**不合并、不推主干**，等对应 owner 批准后才落地。
- **例外必须留痕**：owner 批准过的例外要落在 commit 或 PR 上，口头授权不算：
  `Governance-Exception: <区域> | approved-by=@<owner> | reason=<一句话>`
- **拿不准就按禁改区处理**：某路径是否属禁改区不明确时，先问，不要自行判定为普通区。
- **禁改区清单本身也是规则**：`.github/CODEOWNERS`、团队契约、CI 与发布门禁脚本的改动同样受此约束——放宽门禁的改动不得由 AI 自行合入。

托管平台是否真的强制拦截（分支保护、required review）与本条无关：**平台没拦住不等于可以改**。

## 需求分流

### 必须走完整管线的需求

以下需求必须按“完整需求管线”执行：

- 新功能或跨模块改动；
- 新增或变更接口、数据模型、持久化数据或公共行为；
- 涉及业务规则、计费、额度、权限、安全、文件格式或兼容性；
- 实现路径不明确，或存在多个合理方案的需求。

### 可豁免设计、拷问与计划的改动

机械性改动、明显且局部的简单 Bug、纯局部样式调整，可跳过“头脑风暴、对抗式拷问、设计冻结、实现计划”环节，但仍须自审和执行相称验证。

只有同时满足以下条件才可豁免：

1. 改动仅限单一、明确的局部行为或视觉表现；
2. 根因与预期行为可从现有代码、测试或可复现现象直接确定；
3. 不改变公共接口、数据模型、持久化数据、IPC、安全、权限、计费或文件兼容性；
4. 不需要新增依赖、抽象层、配置项或跨模块协调。

任一条件不满足，必须回到完整需求管线。不得将复杂问题标为“简单”以规避门禁。

## Spec-Driven Development（SDD）强制规范

本规范是全局强制组成部分，适用于所有项目的所有任务。完整 Prompt 见 `~/.codex/ai-change-implementation-prompt.md`（唯一全文）；以下为强制要点，两者冲突时以全文为准。

- **修改本规范任何条款时，必须同步更新 `~/.codex/ai-change-implementation-prompt.md` 全文**，防止两份真源漂移。

### 业务真相（Truth Gate）

- 合法真相源：Approved/Active Spec > API/Event/Data Contract > Architecture/Design 约束 > AGENTS.md 项目规则 > 明确批准的变更。
- **现有代码 ≠ 业务真相；现有测试 ≠ 期望行为**。README、示例、历史 ADR、Git 历史、AI 推断、行业惯例均不能自动定义业务正确性。
- 每个任务开始前回答 `What defines correctness for this task?`；答案为空 → 进入 Requirement Discovery，禁止直接实现。

### Spec 文件组织（Hybrid / 分层 colocated）

Spec 分两类管理，**不允许把全部 Spec 塞进一个中央目录，也不允许全部 colocate**：

- **模块私有 Spec**（能明确归属于一个业务模块的行为与边界）：与模块代码 colocate，放模块内 `spec/` 子目录（如 `src/modules/order/spec/overview.md`、`packages/billing/spec/`）。修改模块业务逻辑时，同目录 `spec/` 是默认上下文，防漂移。
- **全局 / 跨模块 Spec**（跨模块规则、统一权限模型、全局订单生命周期、API 约定等）：放中央 `specs/`（如 `specs/cross-domain/refund-policy.md`），跨模块规则的唯一权威源。

强制规则：

1. Spec 与**业务模块** colocate；**禁止与任意技术目录 colocate**（`controllers/spec.md`、`repositories/spec.md`、`components/spec.md` 是反模式）。
2. 模块私有 Spec 引用上层跨模块规则（Governing Specs），**不复制规则正文**；一条规则只维护一个 authoritative source。
3. 复杂模块可用 `spec/` 子目录拆分（`overview.md` / `creation.md` / `refund.md`），不要求单文件。
4. 中央 `specs/` 保留索引与 Traceability；模块内 `spec/` 无需重复索引。
5. 归属判断：能明确归属某业务模块 → colocate；跨模块/全局/无模块归属 → 中央 `specs/`。

### 任务九分类

每个任务先分类，不得默认 Bug 都是代码 Bug：A. New Feature / B. Requirement Change / C. Implementation Bug / D. Missing Requirement / E. Incorrect Requirement / F. Architecture Limitation / G. Data Issue / H. External Dependency Issue / I. Non-behavioral Change。

处理路径：

- **C. Implementation Bug**（Spec 对、代码错）：不改 Spec → 根因 → 修实现 → 补回归测试 → 验证。
- **D. Missing Requirement**（Spec 未定义）：禁止从代码/测试/常识推断业务规则；Truth Source=undefined → Requirement Discovery → 决策 → 更新 Spec → 实现。
- **E. Incorrect Requirement**（Spec 本身错）：**立即停止 Bug 修复流程** → 重分类为需求变更 → Change Proposal → 澄清/ask-grill → 决策 → 更新权威 Spec → 重规划 → 实现。禁止修 Bug 时静默改变业务行为。
- **F. Architecture Limitation**：Design Proposal → Impact Analysis → 更新 Design/ADR → 必要时更新 Contract → 重规划 → 实现。禁止绕过架构约束打补丁。

### Requirement Change Gate

任何改变外部可见行为的修改（用户可见行为、API、Event、状态、权限、金额、业务计算、数据保留、默认策略、通知、状态转换、第三方集成、兼容性行为）必须走：

```text
Change Proposal → 澄清 → 决策 → 更新权威 Spec → 重规划
```

Change Proposal 模板：Current Behavior / Problem / Proposed Behavior / Reason / Affected Areas / Risks / Open Questions。未经确认不得当正式 Spec。

### Impact Analysis

任何行为变更实施前执行，至少检查：Canonical Spec、Dependent Specs、Domain modules、State machines、Permissions、API/Event contracts、Data model/migrations、Backend、Frontend、Tests、Logging/monitoring、Compatibility、Documentation。输出 Affected / Possibly affected / Not affected。

### 先更新知识，再实现

正式业务行为变化：先更新 Spec；涉及架构：先更新 Design/Architecture/ADR；涉及外部结构：先更新 API/Event/Data Contract；然后才进入实现。

### Skill 边界

ask-grill 只负责 Discover / Challenge / 暴露假设，其输出 ≠ 正式业务真相；Superpowers 只负责 Design / Plan / Implement / Test / Verify，不得擅自修改已批准需求。任何阶段发现上游问题（Requirement / Spec / Design / Contract）必须 STOP → Change Proposal → 决策 → 更新 → 重规划；禁止为了让测试变绿而修改需求或测试期望。

### 沟通规则

发现需求问题时不得直接决定，必须向用户说明：Current approved behavior / Observed problem / 分类判断（Implementation Bug / Requirement Gap / Incorrect Requirement / Architecture Limitation）/ 变更所需决策。任务本身已含明确批准的新行为则无需再确认。

### 收尾输出

每次任务结束输出 Execution Summary（Classification / Truth Source / Changes / Spec-Design-Contract Updates / Tests / Verification / Remaining Risks-Follow-ups）；实现类任务结束前执行 Reconciliation（Spec/Design/Contract/Code/Tests 逐项 ✓/issue）与 Document Drift Check（搜索旧术语/旧参数/旧状态/旧 API/旧 Event，语义判断后处理，禁止机械全局替换）。

### 不可协商规则（10 条）

1. 修 Bug 时禁止静默改变业务行为。
2. 禁止把现有代码当业务真相。
3. 禁止把通过的测试当作需求正确的证明。
4. 禁止让 ask-grill 输出自动成为 Spec。
5. 禁止让实现便利重新定义已批准业务行为。
6. 业务行为未定义时停止实现，进入需求发现。
7. 实现暴露需求/设计问题时回到上游重规划。
8. 已批准的行为变更必须先更新 Spec 再实现。
9. Spec 只保留当前真相，历史理由进 ADR / Git。
10. 优先最小连贯变更，禁止机会主义重构。

## 完整需求管线

设计冻结前禁止编写实现代码。所有阶段均有门禁，不得事后补录为仪式。

| 阶段 | 共同必经行为与产物 | Claude Code 执行方式 | Codex 执行方式 |
| --- | --- | --- | --- |
| 1. 提出需求 | 逐字记录原始诉求；不作业务臆测；业务逻辑不明确时向用户核实 | 收到需求后立即触发 `superpowers:brainstorming` | 立即开展等价澄清 |
| 2. 头脑风暴与澄清 | 形成目标、范围、排除项、关键决策、风险与成功标准 | `superpowers:brainstorming` | 等价的设计分析 |
| 3. 对抗式拷问 | 以反方视角发现遗漏、矛盾、未决问题、边界情形和既有代码冲突；逐条记录结论 | `grilling` | 等价的反方复核 |
| 4. 修订并冻结设计 | 根据拷问结论形成冻结版 spec，并取得用户确认 | 按确认后的 spec 推进 | 按确认后的 spec 推进 |
| 5. 编写实现计划 | 拆为可独立执行、带验收标准的步骤并存档 | `superpowers:writing-plans` | 等价的可执行计划 |
| 6. 执行 | 仅按冻结 spec 实现；按任务性质拆分独立工作与检查点 | `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` | 等价的拆分执行或检查点机制 |
| 7. 测试、审查、验证与收尾 | 按下文的测试、审查与验证门禁完成交付 | 使用对应的审查、验证、分支收尾 Skill | 执行等价行为并提供证据 |

Claude Code 的 Skill 名称是其必经执行方式；Codex 不依赖不存在的同名 Skill，但不得以此为由跳过相同的行为、产物或门禁。

## Bug 根因门禁

发现疑似 Bug，禁止直接在症状层打补丁。

### 非显然 Bug

行为异常、间歇性问题、跨模块问题，以及涉及数据、计费、额度或权限的疑似 Bug，必须先由独立子 Agent 完成复审，再动手修复：

1. **真实性复核**：给出复现路径、触发条件、预期与实际行为，并排除用例错误、环境/数据问题和对预期的误解；
2. **根因与影响面复核**：追溯真正起因，列出所有调用方与受影响路径。

复审通过后，必须从根因系统性修复，并重新审查整处改动是否消除根因且未产生副作用。禁止 catch 吞错、条件绕过、延迟、重试、复制粘贴另一套逻辑等症状级补丁。

Claude Code 必须用 Agent 工具派发独立子 Agent，并遵循 `superpowers:systematic-debugging`；Codex 必须派发独立子 Agent 执行等价复核。独立复审资源不可用时，非显然 Bug 不得降级为“简单 Bug”直接修改，应如实报告门禁无法满足。

### 简单 Bug

一眼可见的拼写、常量、操作符或单处样式问题可由主 Agent 直接修复，但仍须确认直接根因并执行针对性验证。

## 代码质量红线

约束产出代码本身的质量，适用于所有实现类改动（纯文档、格式、重命名除外）。与「最小充分方案」原则配套，违反任一条即视为未完成，必须在宣称完成前修正。

- **1. 死代码**：禁止保留未被引用的 import、变量、函数、分支、配置项与文件；改动后被取代的旧实现立即删除，不留“以防万一”的悬空代码；重构用的临时开关/特性门在合并前清除。
- **2. 冗余代码**：重复 ≥3 次的逻辑必须抽取复用，第二次出现先打 `TODO(owner)`；同义但不同形的实现不得并存（如多套 HTTP 客户端、多套日期格式化）。**复用优先，禁止另起平行实现**：写任何代码前先搜项目内是否已有相同/相似实现（组件、Hook、Service、工具函数、Schema、配置）；已有则**复用或扩展，禁止明知存在仍重写一套**（改名重写、换形态重写、换个模块重写均算）；确有业务差异需新建时，说明与既有实现的区别并尽量复用其可复用部分。
- **3. 过度设计**：不为单一实现造抽象层/工厂/策略/接口/注册表/配置项，不为假设的未来扩展预留枚举/接口方法/扩展点；先有 ≥2 个真实需求再抽象。
- **4. 过度防御**：无证据不得加判空、try/catch 兜底、重试、降级或参数二次校验；不得用 catch、条件绕过或复制另一套逻辑掩盖错误或绕过门禁。安全、数据正确性、权限、兼容性及已有规则明确要求的错误处理不属于过度防御，不得省略。
- **5. 空壳与未完成代码**：禁止交付空函数、桩实现、`throw 'todo'`、未接通路径或 `TODO 未实现` 占位；未实现的分支必须显式报错并提示用户，不得假装能用；不得引入 mock service / mock fallback 假装功能就绪。
- **6. 重造轮子**：先查是否有仍在维护的开源方案能直接满足；若有合格候选，必须列出多个选项（名称 + 一句话差异 + 推荐项）供用户确认，确认后再接入，禁止自行选定后直接手写替代；手写仅限“无合格开源 / 100 行内可替代 / 业务强相关无通用库”三种情况。合格阈值与禁用清单以各项目 `AGENTS.md` 为准。
  - **写代码前先搜方案（实现期门禁）**：实现任何非平凡能力前，必须先搜索项目内已有实现/依赖（复用规则见「冗余代码」）并评估仍在维护的开源方案，写明「复用 / 用库 / 手写+理由」的决定；有合格开源候选时列出选项供用户确认，**禁止不经搜索直接手写**。
  - **「100 行内可替代」不豁免通用能力**：日期、CSV、UUID、校验、状态机、图片处理等已有成熟库的通用能力，手写仍需说明理由并取得用户确认，不得以行数少为借口跳过。
- **7. 架构不统一**：新代码必须沿用本项目既有分层与单向依赖方向，不另起风格、不跨层调用、不绕过既有 service 直接操作底层；同一意图只允许一套实现入口。具体分层以各项目 `AGENTS.md` 为准。

## 测试、审查、验证与收尾

### 测试分流

- 新增或变更业务行为、接口、数据逻辑以及 Bug 修复：新增或更新测试用例不是完成门禁；必须运行相关验证命令，可根据任务风险、现有测试缝隙和执行上下文决定是否补充测试。
- 纯局部 UI 或样式调整：执行相称的已有组件测试、视觉/交互验证或截图检查；可在存在合适测试缝隙时补充测试，禁止为凑流程编写脆弱的实现细节测试。
- 纯文档、规则、注释、格式或重命名：必须执行链接、格式、diff 和相关静态检查。

### 审查与完成条件

- 功能、跨模块改动、非显然 Bug，以及安全、数据、权限、IPC、文件边界改动，必须由独立 reviewer 审查。审查覆盖 spec 符合性、根因是否消除、回归与安全边界；反馈逐条处理或说明拒绝理由。
- 获豁免的机械改动、简单 Bug、纯局部样式调整和文档规则改动，至少必须由主 Agent 完整自审 diff。
- 所有实现类改动完成前必须清理调试代码、临时日志与无效注释，检查类型、错误处理、安全边界和相关文档，并运行与改动相关的验证命令。
- 未提供真实的 lint、类型检查、测试、构建或其他相关验证命令及结果，不得宣称完成。
- 无法取得高风险改动所需的独立 reviewer 时，不得宣称完成，应明确报告未满足的审查门禁。

### 完成前代码质量自审清单

所有实现类改动在宣称“完成”前，必须针对本次 diff 逐条自审并修正，任一条不达标不得宣称完成：

- 无未引用的 import / 变量 / 函数 / 分支 / 文件（死代码）。
- 无重复 ≥3 次仍未抽取的逻辑，无同义多套实现（冗余）。
- 无为单一实现新增的抽象层 / 工厂 / 接口 / 配置项 / 预留扩展点（过度设计）。
- 无无证据的判空 / try-catch 兜底 / 重试 / 降级；有证据的安全与数据正确性校验不在此列，不得误删（过度防御）。
- 无空函数 / 桩 / `throw 'todo'` / 未接通路径 / `TODO 未实现` 占位（空壳）。
- 无自造已有合格开源方案可替代的能力；若存在合格开源候选，已列出选项并经用户确认后再接入（重造轮子）。
- 新代码的分层与依赖方向与本项目既有结构一致，无跨层调用 / 另起风格（架构统一）。
