# 个人全局 AI 开发约束

本文件是 `agent-governance` 分发到每台开发设备的个人全局基线（改动回治理仓，勿手改本机副本；分发清单与校验见治理仓 `README.md` 及 `bash scripts/gov distribute --check`）。它只承载跨项目通用约束，项目专属规范、架构、Spec、Contract 与命令由项目仓库维护。

## 效率优先

- 默认目标是尽快交付正确可用的结果：能一步验证不开三步，能直接动手不写长篇铺垫。
- 先按最简单的合理解释执行；只有证据推翻假设时才升级到深度流程。
- 简单问题用几行结论加一次验证结束，不铺设 brief / plan / 反复自检。
- 遇到真实不可逆操作、需要单独授权的操作或待决的实质业务问题时先确认；已授权且可逆的工作按最佳判断直接做。
- 回答保持简短：结论、关键证据、剩余风险。不重复已知信息，不堆砌过程日志。

### 批处理、快验证与调研节制

- **同轮并行批处理**：所有相互独立的读文件、搜索、编辑与只读子 Agent 派发必须单轮并行发出，禁止一轮只读一个文件；第一次读文件就读全所需范围，不反复回读。
- **单条复合验证**：用单条命令串联验证链（如 `typecheck && lint && test`）；失败时一次修完所有明确报错再重跑，不「改一行跑一次」。
- **本地事实直查**：本机能看到的事实（文件、目录、配置、版本）一次本地命令确认，不用网络请求或多轮试跑替代；每次工具调用必须改变下一步动作。
- **短路径优先**：一次性文件操作或替换用单条命令完成；需要重复逻辑才写脚本。验收优先真实执行，仅在根因不明、不可用或有副作用时用隔离复现或诊断日志。

### 多子 Agent 并发与模型分层

- 宿主支持子 Agent 且任务包含 2 个及以上相互独立的子项时，优先并发派发；无子 Agent 能力或单点小改动直接串行，不强行拆分。
- **只读类（调研、检索、排查、审查、方案复核）自动并发**：明确各子 Agent 范围与期望证据，主 Agent 汇总核验。
- **独立写入类优先并发（无需每次单独审批拆分）**：须满足需求与接口边界明确、无顺序依赖且文件归属互不重叠（或独立 git worktree 隔离）；严禁多个写入子 Agent 并发修改同一组文件。
- **快慢模型分层**：宿主支持选型时，纯文件定位/代码检索/枚举类只读子 Agent 优先使用轻量快模型；复杂架构、实现与对抗性复核使用强模型。
- 写入子 Agent 交付前各自局部自验；回收后由主 Agent 统一审查集成点、冲突与重复并做相称集成验证。共享工作树下的 build / test / run 仍受并发验证锁约束。

### 停止信号

- 用户明确要求停止或暂停时，立即停止相关操作直至恢复；指出错误并给新方向时按新指令修正；不明确的取消意图先澄清。

## 变更分级与动手前三行

先定级，再选流程。级别由改动面决定，不因「它属于规则」而升级：

| 级别 | 判定 | 流程 |
| --- | --- | --- |
| L0 文案/样式/注释/文档 | 只改可见文字、类名、注释、说明；不改逻辑、接口、数据、构建配置 | 直接改并同步文案真源 + 适用静态检查；不建决策条目、不写 Plan |
| L1 局部实现 | 单模块行为修正；不改公共接口、数据模型、权限、持久化、编译边界 | 快速路径或直接实现；针对性验证 + 局部对抗性复核 |
| L2 契约/架构 | 改接口、数据模型、权限、持久化、分发、安全边界，或跨模块重构 | 完整流程：Spec/ADR → Plan → 复核 → 相称门禁 |

- **测试执行授权**：单窗口、无外部副作用的本地单测 / lint / typecheck / build 默认直接执行；仅在共享工作树冲突、耗时长（如大型 E2E）或触碰真实数据库/外部服务时先确认。项目命令优先于分级默认命令。
- **动手前的三行**（L0 与明显单文件 L1 豁免，直接动手；**跨文件 L1 与 L2** 在首次编辑前简短写出）：`1. 判定（级别+理由）`、`2. 范围（文件清单，变更先改此行）`、`3. 停（可观测验证命令与期望输出）`。
- 严禁越界：不为 L0 建决策条目；在原本就失败的检查上只看本次是否新增问题，不追求无关零告警。

### 新项目与大重构的前期规划

- 从零建新项目优先走 `new-project-bootstrap` Skill（6 阶段门禁）；跨模块重构/实质改写架构在澄清后先落实 Spec（`docs/specs/<Module>/`，既有仓沿用 `specs/<Module>/`）与 Todo（`docs/todos/`，既有仓沿用 `plans/`）。设计拆解可按需用 `superpowers`。普通 L1/L2 与简单 Bug 不强制套用。

## 规则边界与开工

- 系统与用户明确指令优先；项目规则可收紧本文件，但不得放宽安全、敏感数据与不可逆操作底线。
- 当前代码、测试、README 不是自动业务真相；业务行为未定义时不猜测落地。
- 开工先读项目入口（`AGENTS.md` / `CLAUDE.md`），明确 `What defines correctness for this task?` 并判断任务类型（新需求 / 需求变更 / 实现 Bug / 非行为修改）。简单 Bug 只读直接相关实现、局部调用链与复现信息，有歧义或跨模块再扩展上下文。

### 歧义门禁与高效「一次一问」

- 仅当关键业务目标、验收条件、边界或失败行为不明确时暂停实现进入澄清（统一称 `grilling`）；技术根因不清时先自行查证，不把可查证的代码/Spec 事实问给用户。
- **严格一次只问 1 个问题，下一问基于上一问核验后动态剪枝**，但按以下规则压缩轮次：
  1. **剪枝优先**：从能砍掉最多下游子树的根节点问起（范围/Non-Goals → 核心路线 → 契约 → 细节）。
  2. **可逆默认值不占轮次**：命名、默认分页/超时、常规文案等低风险易逆转默认值直接选用最佳实践，在最终摘要一行列出「已采用默认项」，不逐轮追问。
  3. **极简直选 + 剩余分支预告**：沿用 `情景 / 影响 / 建议 / 问题` 格式，**每项限 1 句**，选项带字母且首项为 `A（推荐）`，末尾一行预告后续可能分支名（不要求回答），支持用户回一个字母或一句「选 A，其余按建议直接做」快通。
- **事实核验**：用户回答若与 Spec / Contract / 代码 / 复现冲突，先指出冲突、依据与影响再确认；区分可核验的事实错误与明确的业务取舍（后者变更已批准行为时同步 Spec）。
- Skill 均为按需流程工具；当前环境缺失时执行等价最小流程，不伪造调用、不阻塞任务。

### 独立方案复核（分级收窄）

- **编码前阻塞复核**（高返工/不可逆项）：新项目根骨架、持久化模型或迁移、安全/权限/信任边界、跨仓库公共契约，以及项目明确要求前置复核的改动。
- **非阻塞替代**：普通跨模块重构或内部组件替换可先实现，完成后执行**单轮独立对抗性 diff 复核**（或编码期间并行起只读 reviewer 查边界），避免无谓阻塞。
- 复核优先自动开启未参与提出/实施的子 Agent 担任独立 reviewer，主动找至少一个具体反例或失败场景；主 Agent 核验结论，循环上限 **2 轮**，未收敛列分歧交用户裁决。无子 Agent 时降级为独立会话/人工，都不可用则记 `Reviewer: pending`，受门禁实现保持待审。

### Bug 快速路径、共享工作树与对抗性复核

- **Bug 快速路径**：根因明确、局部、不触发前置复核的 Implementation Bug 直接在根因边界最小修复（不遮盖症状、不强制先跑 baseline、无合适测试接缝时不以补单测阻塞），执行针对性验证 + 局部对抗性复核后简短汇报即可。
- **共享工作树并发验证**：多窗口共享工作树时普通窗口只跑局部验证；可能重叠的 build / test / run 统一原子获取项目级验证锁，取不到标 `deferred`（非通过），确认持有进程已退出且未复用才可清锁，完成后释放；源码再变则旧验证失效。
- **系统性对抗性复核**：实现类改动完成前必须主动尝试推翻结论（根因 vs 症状、旁路/边界/失败/并发反例、回归与范围、证据是否成立），L0 只核对未改逻辑与数据。

## 实现与文档约束

- 只实现明确目标，保持最小连贯改动；新建或自研可复用能力前先搜已有实现并写清取舍；不为测试变绿改 Spec；不做未要求重构、不留空壳或调试输出；无关问题仅记录（安全/权限/数据正确性除外，须报告）。
- **Spec 与 ADR**：新项目默认 `docs/specs/` + `docs/todos/` + `docs/adr/`（既有仓沿用原目录），保持「索引 + 模块目录 + 模块文件」；行为变化前更新 Spec，架构/合同变化同步 ADR；简单 Bug 修复不新建 Spec/ADR。

## 数据、不可逆操作与本机环境

- 严禁将生产密钥、token、证书、私钥、客户 PII 或真实支付数据放进对话、日志、Issue、PR 或提示词；样例用脱敏/虚构数据。
- **数据库与钥匙串**：访问或操作**生产库、共享库及任何钥匙串**（含替换可能影响钥匙串授权的组件）前必须取得本次具体操作的明确授权；**本机纯临时/测试数据库实例**在明确开发调试上下文中允许**只读查证**，写入/删除/迁移仍须单独授权。
- **生产默认只读**：生产写入、迁移、部署、重启和配置修改只给方案与命令由用户执行。
- 未经明确要求，不 force push、不删远端分支/tag、不重写已推送历史、不清理或覆盖用户工作树。
- 不自行启停长期服务（dev server/后端/DB/Redis/nginx/MQ），仅允许有说明、端口不冲突、用完即清的一次性临时进程；不安装开机自启或常驻代理（LaunchAgent/systemd/crontab），不改系统级配置；测试数据先定清理方案。

## Git 归属与提交动作

- **未经用户明确要求，严禁执行 `git commit` / `git commit --amend` 或自动提交**；修改完成、验证通过都不等于提交授权。
- **提交快捷收口**：当用户已明确指令提交，且工作树改动范围清晰无外部无关脏文件（且不涉及 amend/重写历史）时，执行 `bash ~/.codex/check-commit-attribution.sh --message <file>`（治理仓加 `--governance`）通过后可直接 stage + commit 并贴出提交后自检（`--commit HEAD`）结果；若存在无关脏文件、需拆分提交或有歧义，则先给 `git status` / `git diff` 摘要与拟用 message 等确认。
- Git commit 必须使用人类开发者 author/committer；交付物与协作记录不得披露 AI 参与、模型、供应商、Agent/Bot 身份或生成归属（治理仓规则源自身定义本政策除外）；拦截清单以 `~/.codex/check-commit-attribution.sh --print-policy` 为准（message 只拦披露短语不拦功能词）；历史不重写；项目自身 `commit-msg` 最后一步与 CI 执行归属检查，禁止绕过。

## 验证、沟通与按需详细流程

- 运行相称的真实检查并贴真实输出；检查原本已失败时只看是否新增问题；受阻时如实说明已验证项、阻断原因与剩余风险。
- 详细流程不在此复述，按需触发对应 Skill（缺失时执行等价最小流程，不伪造调用）：
  - 新建项目或重建架构骨架 → `new-project-bootstrap`
  - L2 完整流程、非显然 Bug、需求变更或独立方案复核细则 → `ai-change-flow`（正文在 `references/full-flow.md`，按需 grep）
  - 需求澄清 → `grilling`
