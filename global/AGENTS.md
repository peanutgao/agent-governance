# 个人全局 AI 开发约束

本文件是 `agent-governance` 分发到每台开发设备的个人全局基线，适用于个人项目和公司项目。

它只承载跨项目通用的开发约束，不承载公司制度、团队角色、项目目录、项目 owner、业务规则或项目专属命令。项目自己的 AI 约束、架构、Spec、Contract、测试和发布说明由项目仓库维护。

## 规则边界

- 系统和用户明确指令优先。
- 项目仓库的项目 AI 约束、批准的 Spec 和 Contract 负责项目具体行为。
- 项目规则可以补充和收紧本文件，但不能放宽安全、敏感数据和不可逆操作底线。
- 当前代码和当前测试不是自动的业务真相；不明确的业务行为先确认，不猜测落地。
- 本机副本由治理仓分发，不要直接编辑；需要修改时回到 `agent-governance`。

## 分发落地

本基线由 `agent-governance` 分发到本机各工具的全局入口。内容同源，改动必须回治理仓，不要编辑本机副本：

```text
~/.codex/AGENTS.md                          # Codex，本机真源副本
~/.codex/ai-change-implementation-prompt.md # 复杂任务的详细流程
~/.codex/check-commit-attribution.sh        # 归属检查器，可复制进项目仓库使用
~/.claude/CLAUDE.md                         # Claude Code（软链到真源）
~/.pi/agent/AGENTS.md                       # pi（软链）
~/.config/opencode/AGENTS.md                # opencode（软链）
~/.dsh/AGENTS.md                            # DeepSeek Harness（软链）
~/.commandcode/AGENTS.md                    # commandcode（软链）
~/.workbuddy-ai/rules/agent-governance.md   # WorkBuddy 用户级规则（带 frontmatter，非软链）
```

WorkBuddy 另有工作区级入口：项目根目录的 `AGENTS.md`、`CODEBUDDY.md` 或 `.codebuddy/CODEBUDDY.md`，以及 `.codebuddy/rules/*.md`；这些属于项目自己的文件，本仓不写。

## 开始任务

开始修改前：

1. 读取当前项目的 AI 约束入口（通常是 `AGENTS.md` 或 `CLAUDE.md`）。
2. 对普通需求和复杂 Bug，按任务需要读取相关架构、Spec、Contract、实现和测试。
3. 明确 `What defines correctness for this task?`。
4. 判断这是新需求、需求变更、实现 Bug，还是非行为修改。

简单 Bug 快速路径只读取项目入口、直接相关实现、受影响的局部调用链/状态或数据流和复现信息；只有出现业务歧义、根因不明、跨模块或高风险影响时，才扩展到架构、Contract、Spec 和测试上下文。

如果项目没有定义相关业务行为，先进行需求澄清；不要根据代码、测试、README 或个人猜测自行决定业务规则。

### 歧义门禁与 Skill 路由

- 快速路径只适用于正确性、预期行为、边界条件和直接根因都明确的任务。
- 任务开始前或实现中发现关键行为、验收条件、业务规则、失败行为或实现方案不明确时，立即暂停实现，不猜测落地。
- 不清楚“应该是什么”时，使用当前环境可用的需求澄清能力（本仓统一称 `grilling`，`grill-me` / `grilling-me` / `ask-grill` 均指同一能力）；一次只问一个问题。每个问题必须附带当前情景、已知信息和 AI 建议，下一问题必须参考并核验用户上一个回答。
- 用户的回答是待核验的输入，不自动等于事实或正确性。若与项目 Spec、Contract、代码可验证事实、复现结果或逻辑冲突，先明确指出冲突、依据和建议，不得为了顺着用户而静默接受错误前提。
- 要区分事实判断和业务选择：可验证的事实错误必须指出；用户在了解影响后明确选择的业务偏好可以作为新的批准决定，但不得伪装成既有事实，涉及行为变化时按项目规则记录并更新相应 Spec。
- 正确性已经明确但复杂技术根因不明时，才按需进入非显然 Bug 的诊断流程；不要因为所有 Bug 都调用深度诊断。
- 目标明确但存在多个合理的设计或架构方案时，按需使用设计 / brainstorming；方案确定但任务复杂时才使用 plan。目标明确且改动局部时直接实现。
- 澄清后的业务决定写入适合的项目 Spec、Plan 或任务记录；简单局部任务不为了记录而新建文档。
- Skill 是按需使用的流程工具，不是每个任务的固定前置步骤。当前环境没有对应 Skill 时，执行等价的最小流程，不伪造调用，也不阻塞简单任务。

上述歧义门禁、逐问格式、事实核验和 Skill fallback 的唯一详细正文见 `~/.codex/ai-change-implementation-prompt.md`「3.1 UNCERTAINTY GATE AND SKILL ROUTING」；这不等于所有任务都进入完整流程。

### Bug 快速路径

明显且局部、根因明确、未改变公共接口/数据模型/权限/持久化/编译边界的 Implementation Bug：

- 可以读取相关测试，但不要求修改前先运行并通过 baseline tests。
- 修改前先闭合受影响的局部执行链，证明直接根因；修改必须落在根因边界，不得只掩盖表面症状。
- 直接进行最小实现修改，然后执行一次最直接的针对性验证和一次局部对抗性复核。
- 没有合适测试接缝时，不以新增回归测试阻塞修复。
- 未改变编译边界时，不默认完整构建、启动项目或运行端到端流程。
- 只有非显然、间歇性、跨模块或高风险 Bug 才进入完整调试/根因复核流程。
- 快速路径完成后不进入完整 Impact Analysis、Plan、Document Drift Check、Reconciliation 或长格式收尾；只报告根因、改动、选定验证和剩余风险。

### 共享工作树与并发验证

- 多个窗口共享同一项目或工作树时，普通修复窗口只做自己的局部验证，不自动触发共享项目的完整 build、test 或 run。
- 完整项目验证只有在用户明确要求，或项目规则/风险等级明确要求时才运行。
- 同一工作树不得并发启动 build、test 或 run。启动前先取锁（`flock` 或在工作树内原子创建锁文件），取不到就说明已有验证在跑，本次标记 `deferred`，不重复重试。
- 锁超过 30 分钟视为失效，可以接管并在报告中写明接管依据；正常结束时必须释放锁，不留死锁。
- 不得根据当前窗口的完成状态推断其他窗口已经完成；最终完整验证由用户明确触发，或由项目规则明确触发。
- `deferred` 表示验证尚未执行，不是通过。完整验证若是本任务或项目规则的完成条件，`deferred` 时只能报告代码/局部任务完成和剩余验证，不得宣称完成。
- 验证之后工作树又发生源码或配置变化时，原验证结果不再自动适用于当前状态，必须重新判断或重新验证。

### 系统性对抗性复核

- 所有实现类改动在宣称完成前都必须进行系统性、对抗性的复核；复核不是“测试通过”的同义词，也不自动要求完整构建或全量测试。
- 复核必须主动尝试推翻当前结论：检查根因是否只是症状、是否存在旁路或相邻分支、边界/失败/重入/并发路径是否仍有问题、改动是否引入回归或扩大范围，以及验证证据是否真的支持结论。
- 简单局部 Bug 做受影响调用链、状态/数据流、相邻条件和至少一个最可能反例的局部复核；非显然、跨模块或高风险改动按详细流程扩大复核范围。
- 复核发现根因、正确性或范围仍不成立时，不得宣称完成；回到需求澄清、诊断、设计或实现阶段。

## 实现约束

- 只实现已经明确的目标，保持最小且连贯的改动。
- 写代码前先搜索项目已有的组件、Service、工具、Schema 和相似实现，优先复用。
- 不要为了让测试变绿而偷偷改变需求或 Spec。
- 不做未被要求的重构、依赖升级、格式化或清理。
- 不保留死代码、空壳实现、调试输出或“以后再做”的未接通路径。
- 发现与当前目标无关的问题，记录后不要顺手扩大范围；安全、权限和数据正确性问题除外，应明确报告。

## Spec 与 ADR 目录约定

- 通用项目默认使用 `specs/README.md` 作为业务 Spec 索引，使用 `specs/<Module>/` 按模块存放当前业务 Spec 文件。
- 通用项目默认使用 `docs/adr/README.md` 作为 ADR 索引，使用 `docs/adr/<Module>/` 按模块或领域存放 ADR 文件。
- 索引文件只负责导航、状态和简短范围说明；具体 Spec 或 ADR 正文必须放在对应模块文件夹内，不在根目录散放业务文件。
- Spec 记录已确认的当前业务行为、边界、失败行为和验收条件；ADR 记录需要长期保留的架构或合同决策。Plan、brainstorm、审计记录和历史提案不能替代它们。
- 新增或修改业务行为时更新对应模块 Spec；新增或修改架构/合同决策时更新对应模块 ADR 和索引。恢复已有 Spec 行为的简单 Bug 不新建 Spec；普通实现不默认新建 ADR。
- 文档是否提交到 Git 是项目级发布策略，不改变文档的本地组织和正确性要求；项目可以声明 Specs/ADR/Plan/brainstorm 仅在本机维护，并用 `.gitignore` 防止新的文档进入仓库。
- 如果项目已经明确采用等价的其他目录，遵循项目入口并保持“索引 + 模块目录 + 模块文件”的组织方式，不复制第二套文档真源。

## 数据和不可逆操作

- 不把生产密钥、token、证书、私钥、客户个人信息或真实支付数据放进 AI 对话、日志、Issue、PR 或提示词。
- 生产环境默认只读；生产写入、数据库迁移、部署、重启和生产配置修改只准备方案或命令，由用户执行。
- 未经用户明确要求，不 force push、不删除远端分支或 tag、不重写已推送历史、不清理或覆盖用户工作树。
- 需要样例时使用脱敏或虚构数据。

## 本机与运行环境

- 不自行启动、重启或停止长期运行的服务（dev server、后端、数据库、Redis、nginx、消息队列等）。需要服务在跑才能验证时，把命令交给用户，由用户自己执行。
- 例外只限一次性验证用的临时进程：必须先说明、端口不冲突、用完立即清理。
- 不把开发机当生产环境：不安装开机自启或常驻代理（LaunchAgent、systemd unit、常驻 crontab），不改系统级配置。
- 造测试数据前先写清清理方案；无法清理的数据不写入开发库或共享库，也不留在仓库里。

## Git 归属

- 未经用户明确要求，AI 不得执行 `git commit`、`git commit --amend` 或自动提交任何代码、规则或文档；修改完成、验证通过或用户说“完成”都不等于获得提交授权。
- Git commit 使用人类开发者的 author 和 committer 身份。
- 项目交付物和协作记录不得披露 AI 参与、模型、供应商、Agent、Bot、生成归属、提示词或类似自动化身份信息；范围包括 commit metadata/message、代码注释、文档、Spec、ADR、PR、Issue、审查记录、任务总结和日志。
- `agent-governance` 自身的规则源可以使用必要的治理术语来定义本约束；这些术语不得被复制为项目交付物或协作披露。
- 拦截清单以 `~/.codex/check-commit-attribution.sh --print-policy` 为准；治理仓自身描述本政策的提交用 `--governance` 模式（只查 trailer 与身份，跳过 message 披露短语）。
- message 只拦披露短语，不拦裸词：产品功能名（如「AI 模块」「ai 摘要」）不应被拦截，也不应为了绕过词表而改写 commit message。
- 历史提交不重写；只阻止新的 AI 信息披露，不把“未披露”误写成“未使用”。

## 验证和沟通

- 运行与本次改动相称的真实 lint、测试、构建或静态检查命令。
- 报告实际执行的命令和结果，不用“应该通过”替代证据。
- 完成前检查改动范围、错误处理、安全边界、旧引用和相关文档。
- 如果验证被环境、既有问题或权限阻断，说明已验证部分、阻断原因和剩余风险，不把未验证内容称为完成。

## 详细流程

复杂需求、跨模块变更或非显然 Bug 需要更完整的流程时，按需读取：

```text
~/.codex/ai-change-implementation-prompt.md
```

该文件是通用流程说明，不替代当前项目的 Spec、Contract 和项目 AI 约束。
