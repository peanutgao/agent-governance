# 变更与实现详细流程

本 Skill 是 `agent-governance` 详细流程的**触发式**入口，取代过去「在 AGENTS.md 里写一句
『按需读取 ~/.codex/ai-change-implementation-prompt.md』、指望模型自觉去读」的做法。

## 何时加载

只有下列情形才需要本 Skill 的完整流程。其余任务按 `global/AGENTS.md` 的分级直接做：

| 触发条件 | 加载哪一节 |
|---|---|
| 任务被判为 **L2**（改接口、数据模型、权限、持久化、分发、安全边界，或跨模块重构） | 全文 |
| Bug 的**直接根因不明**，或非显然、间歇性、跨模块、高风险 | 全文 + `references/full-flow.md` §5–§6 |
| 需求**变更**（已批准行为要改） | `references/full-flow.md` §10 Requirement Change Gate |
| 方案命中**独立方案复核**门禁 | 下面的「独立方案复核」一节 |
| 需要**需求澄清**（不清楚应该做什么） | 改用 `grilling`；路由表见下 |

L0（文案/样式/注释/文档）与普通 L1（单模块局部实现）**不加载本 Skill**，直接按
`global/AGENTS.md` 执行。

## 唯一真源

完整正文在 `references/full-flow.md`，随本 Skill 一起分发到各工具的 skills 目录。
需要某一节时用 `grep -n '^## '` 定位再读该段，不要整篇读入——这是渐进加载的意义。

## 变更分级

| 级别 | 判定 | 流程 |
| --- | --- | --- |
| L0 文案/样式/注释/文档 | 只改用户可见文字、类名、注释、说明；不改逻辑、接口、数据、构建配置 | 直接改并同步文案真源；项目适用的静态检查；跳过 Impact Analysis、独立复核、Plan、文档漂移检查；不建决策条目 |
| L1 局部实现 | 单模块行为修正；不改公共接口、数据模型、权限、持久化、编译边界 | Bug 快速路径或直接实现；一次针对性验证 + 局部对抗性复核 |
| L2 契约/架构 | 改接口、数据模型、权限、持久化、分发、安全边界，或跨模块重构 | 完整流程：Spec/ADR → Plan → 复核 → 相称门禁 |

- 等级决定默认流程，项目明确要求的验证和按影响触发的独立复核分别判断；单窗口无外部副作用的本地单测/lint/构建默认直接执行，安全与不可逆授权底线优先。
- 仍不确定时严格只问 1 个剪枝收益最高的问题；禁止两个分支都做。
- 跨文件 L1 与 L2 在动手前写下判定、范围与停止条件三行（范围变化先改这三行）；L0 与明显单文件 L1 豁免。

## 歧义门禁

在进入快速路径或开始编码前，以及实现过程中发现新信息时，都要检查关键不确定性。至少确认：

```text
正确行为 / 验收条件是否明确？
边界条件和失败行为是否明确？
当前使用的 Truth Source 是否明确？
如果是 Bug，Expected / Actual / 直接根因是否明确？
```

关键不确定性必须先区分是「需要用户决定的业务问题」，还是「AI 可以自行查证的工程问题」：

- 业务目标、正确行为、验收条件、范围、失败行为或用户取舍未确定时，必须 `STOP implementation`，进入 `grilling`，逐问取得决定；未确认前不得猜测落地。
- 仅技术根因、代码路径或实现细节未确定时，AI 应先通过代码、文档、复现、工具和证据自行调查；非显然、间歇性、跨模块或高风险问题按需进入深度诊断，不因技术不确定性自动等待用户。
- 设计方案不唯一时，AI 先比较方案及其影响；只有方案会改变业务行为、范围、风险接受或需要用户取舍时，才暂停并询问用户。

工程调查可以继续，但不得把尚未证明的根因或方案当成事实；调查发现会改变业务行为、范围或风险时，立即回到用户决策门禁。

### Skill 路由

| 不确定内容 | 使用流程 |
|---|---|
| 不清楚应该实现什么、正确行为、验收条件、边界或失败行为 | `grilling` |
| 正确行为已经明确，但非显然、间歇性、跨模块或高风险的技术根因不明 | `diagnosing-bugs` 或等价的深度诊断 |
| 目标明确，但存在多个合理的实现、设计或架构方案 | design / brainstorming |
| 方案已经确定，但任务复杂、涉及多个步骤或多个模块 | plan / writing-plans |
| 目标、方案和范围都明确，改动局部且无需前置复核 | 直接实现或对应的快速路径 |

Skill 是流程工具，不是硬依赖。当前环境没有对应 Skill 时，不得伪造调用；执行等价的最小澄清、
诊断、设计或计划流程。明确且局部的任务不因 Skill 不可用而阻塞，关键业务决定未确认时则不能继续猜测实现。

### 需求澄清的交互格式（严格一次一问 + 剪枝提速）

严格一次只问 1 个问题，下一问基于上一问核验后动态剪枝，并遵守 4 条提速原则：
1. **剪枝优先**：按能砍掉最多下游子树的顺序从根节点问起（范围/Non-Goals → 核心路线 → 契约 → 细节）。
2. **可逆默认值不占轮次**：命名、常规超时/分页、一般文案等低风险易逆转默认值直接选用最佳实践，在最终摘要一行列出「已采用默认项」，不逐轮提问。
3. **极简直选**：每项限 1 句，选项带字母且首项为 `A（推荐）`，3 秒读完可回字母。
4. **剩余分支预告（支持快通）**：末尾一行仅列出后续可能分支名（不要求回答），允许用户一句「A，其余按建议直接做」直接进实现。

```text
情景：一句话交代当前事实与待决分支。
影响：一句话说明对范围、契约或返工的影响。
建议：A（推荐）... / B ...（一句话理由；建议不是决定）。
问题：选择 A 还是 B？（后续可能分支：<名称1>、<名称2>，视本问结果决定）
```

用户回答只是待核验输入，不自动成为事实或业务真相。下一轮必须先与项目 Spec、Contract、
代码可验证事实、复现结果和逻辑核对，再引用其中没有冲突的内容或指出冲突。不得为了顺着用户
而接受错误前提，不得重复已确认的问题，也不得一次性抛出多个必答问题。

`grilling` 只负责发现假设、暴露缺口和推动决策，不负责把自己的建议变成业务真相。

### 事实核验与尊重性分歧

```text
用户回答
   ↓
与 Spec / Contract / 代码 / 复现 / 逻辑核对
   ↓
无冲突 → 作为当前决策输入继续
有冲突 → 明确冲突、依据、影响和 AI 建议
   ↓
只提出一个需要用户确认的问题
```

冲突时使用以下格式：

```text
情景：你刚才的回答是「...」，当前正在决定「...」。
核对：Spec / 代码 / 复现结果显示「...」。
冲突：这与「...」不一致，可能导致「...」影响。
建议：我建议「...」，理由是「...」。
问题：是否确认采用「...」？
```

- 可通过事实核对的技术、代码、Spec、Contract 或复现判断如果错误，AI 必须直接指出并给出依据，不得附和。
- 用户明确表达的业务偏好或取舍不是「事实错误」。AI 应说明影响和替代方案；用户在了解后仍确认的，才作为新的批准决定处理。若它改变已批准行为，必须进入 Requirement Change Gate。

## 独立方案复核（分级收窄）

下列**高返工/不可逆**条件任一成立，须在改动实现前获得独立结论：

- 新项目的根基础架构；
- 影响安全、权限、信任边界、持久化模型或数据迁移的方案；
- 跨仓库公共 API / Event / Data Contract 变更；
- 项目自身另有前置复核要求。

其余 L2 变更（如普通跨模块重构、内部组件替换）可先实现，完成后执行**单轮独立对抗性 diff 复核**（或编码期间并行派发只读 reviewer 查边界），避免无谓阻塞。

复核按「方案产出 → 独立 reviewer 对抗性评估 → 主 agent 复核 → 修订方案」循环推进，直到
双方对方案达成一致。优先自动开启未参与提出或实施该方案的子 Agent 担任独立 reviewer；
无子 Agent 能力时用独立会话或人员复核，独立性与对抗性要求不变；都没有则记
`Reviewer: pending`，继续可独立进行的查证，受门禁的实现保持待审。

独立 reviewer 须主动尝试推翻方案：核对需求、现有实现、最简可行方案，检查至少一个具体反例
或失败场景，给出「通过」或「需修订」的依据。主 agent 复核 reviewer 结论，不默认接受；
存在分歧时回到方案修订。循环上限 **2 轮**；仍未收敛即停止，列出分歧点交由用户决策，方案保持
待批、不进入实现。已通过方案发生实质变化时，只重新复核受影响的决定。

每轮在方案记录中留下 reviewer 的「通过 / 需修订」结论与依据、主 agent 的复核意见、
修订内容与轮次编号。完成前的代码审查按项目要求另行执行。
