# Superpowers 工作流参考

按需读取对应章节；所有阶段均须服从 `global/AGENTS.md` 与项目 `AGENTS.md` 的分级、授权和 Git 归属底线。

## 1. Brainstorming 与方案对比模板

仅在存在多个合理技术路线或需要新建架构时使用；若项目已有设计模板，以项目为准。

```markdown
# <模块/功能> 方案对比

## 1. 问题与已确认目标
- 业务真相来源（Spec / 决策记录）：
- 明确范围与非目标：

## 2. 现有能力复用排查
- 已搜索的现有模块/组件：
- 可复用部分与关键缺口：

## 3. 候选方案
### 方案 A：<名称>
- 做法 / 优点 / 缺点 / 风险：

### 方案 B：<名称>
- 做法 / 优点 / 缺点 / 风险：

### 推荐方案与理由
- 为什么这是满足当前需求的最简可行方案：

## 4. 契约、数据与兼容性影响
- 受影响的接口 / 状态 / 持久化 / 迁移：

## 5. 验证策略
- 可观测的完成信号与关键反例：
```

## 2. Implementation Planning 任务拆解模板

落到项目已有计划文件或既有文档结构下，不默认在仓库根目录新建散装文档。

```markdown
# 实现计划：<任务名>

## 任务清单
- [ ] 任务 1：<名称>
  - 范围：<精确文件或模块>
  - 依赖：<前置任务或无>
  - 验证：<具体命令与期望输出>
- [ ] 任务 2：<名称>
  ...
```

拆解检查：
- 每个任务边界清晰、可独立验证；
- 遵循 YAGNI 和最小改动原则，不混入顺手重构；
- 若命中独立方案复核门禁，先完成复核再勾选实现任务。

## 3. 实现与测试循环

有合适测试接缝时推荐红-绿-重构，但**不把提交动作绑进循环**：

1. **RED**：先写能区分预期行为与缺陷的最小失败测试（或明确可复现信号）；
2. **GREEN**：在根因边界做最小实现让验证通过；
3. **REFACTOR**：在测试保护下清理本轮新增代码的重复与复杂度；
4. **VERIFY**：执行相称的针对性验证，必要时按授权扩大验证范围（绝不自动 `git commit`）。

## 4. 子代理并行检查（可选）

仅在满足并行门禁（需求冻结、无共享可变状态、拆分经用户确认、目录/worktree 隔离）时启用：
- 每个子代理只负责单一明确切片并自验；
- 全部回收后必须由主会话统一检查接口对齐、重复与冲突，并执行集成验证；
- 任一子任务发现 Spec 冲突或架构缺口时立即暂停，回到需求变更门禁。

## 5. 完成前收尾清单

- [ ] 改动严格落在声明范围内，无无关重构或调试残留；
- [ ] 权威 Spec / ADR / Contract 已按影响面同步；
- [ ] 已执行相称验证并拿到真实输出（非「应该通过」）；
- [ ] 已完成系统性对抗性复核并检查至少一个最可能反例；
- [ ] 汇报 `git status` / 关键 diff / 剩余风险，等待用户明确授权后再执行任何 Git 提交或推送动作。
