# Superpowers 工程准则参考

本文件提供通用工程启发式参考；当与项目 `AGENTS.md` 或已批准 Spec 冲突时，一律以项目规范和 Spec 为准。

## 1. 设计原则
- **简单性优先**：选择能满足已批准需求的最简可行方案，拒绝推测性抽象与过度工程。
- **YAGNI**：不为假想中的未来需求预留工厂、策略层或未使用配置项。
- **适度 DRY**：重复三次再抽象，避免过早把偶然相似的逻辑耦合在一起。
- **先复用再新建**：写新能力前先搜索项目已有组件、Service 与工具；自研时须写清已有候选和关键缺口。

## 2. 测试原则
- 优先测试可观测行为、边界条件、失败路径、幂等与权限，而非内部实现细节。
- 测试必须自洽：不依赖本机 Git 配置、真实 `$HOME`、固定端口或未声明的外部网络状态。
- 不为了测试变绿而私自改写符合 Spec 的测试断言。

## 3. 代码质量与错误处理
- 模块职责单一，遵守项目既有的分层与依赖方向。
- 命名直接表达业务语义，注释解释「为什么」而非复述代码。
- 禁止无证据的 `catch` 吞错、静默降级、空壳实现或伪造兜底数据。
- 错误信息应暴露足够定位上下文，同时严禁泄露密钥、Token、口令或个人隐私数据。

## 4. 安全与边界
- 所有跨边界输入（外部路径、配置、环境变量、归档、用户输入）均按白名单或显式校验处理，失败关闭。
- 文件写入与状态切换优先采用原子临时文件替换，防路径穿越与软链劫持。
- 生产环境默认只读；数据库、钥匙串和不可逆操作必须先获得用户对当次具体操作的明确授权。
