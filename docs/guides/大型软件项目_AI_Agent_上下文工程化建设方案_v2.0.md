# 大型软件项目 AI Agent 上下文工程化建设方案

> **版本**：v2.1（已与 `agent-governance` 落地工具链对齐）  
> **日期**：2026-11-24  
> **适用范围**：前端、后端、移动端、全栈、Monorepo、多仓库及企业级项目（覆盖存量改造与新建项目起盘）  
> **目标 Agent**：Codex、Claude Code、OpenCode、Cursor、GitHub Copilot、Antigravity、WorkBuddy、ZCode 等具备代码检索能力的 Agent  
> **状态**：架构设计参考指南（新建项目可直接经本仓 [`scripts/gov`](../../scripts/gov)（`project init`）与 [`new-project-bootstrap`](../../skills/local/new-project-bootstrap/SKILL.md) Skill 落地；存量仓库先走 P0 只读盘点再增量接入）

## 1. 建设背景与目标

大型软件项目应用 AI Agent 开发时，主要面临以下问题：新会话重复分析项目架构；大量无关上下文消耗模型预算；业务约束和历史决策难以保存；不同 Agent 的项目规则不一致；前端、后端和移动端分属不同仓库时，无法准确分析完整调用链。

本方案建立一套**技术栈无关、跨项目、跨仓库、跨 Agent** 的上下文工程体系，目标包括：

1. **规则一致**：统一开发原则与验证规范，项目规则由各仓库独立维护。
2. **按需检索**：根据具体任务定位文档和代码，而非全量装入上下文。
3. **知识沉淀**：记录难以仅由代码推导的业务约束、架构决策与系统关系。
4. **事实可追溯**：关键结论基于实际源码、接口契约、配置及测试证据。
5. **跨仓库协作**：明确系统边界、仓库关系、共享契约及跨仓库变更流程。
6. **最小侵入**：不强迫改造现有仓库布局或引入独立检索服务。
7. **闭环验证**：所有代码变更按照实际项目工具链完成必要验证，并如实报告未验证项。

**非目标**：不建立全量代码自然语言镜像；不使用 Markdown 代替正式 API 契约；不强制所有任务运行多个 Agent；不以 AOCI、向量数据库或 Sourcegraph 作为默认依赖。

## 2. 总体架构

```text
开发需求
  │
  ▼
AI Agent 执行层（Codex / Claude Code / OpenCode）
  │
  ▼
指令层（通用原则 / 项目规则 / 任务约束）
  │
  ▼
知识层（架构 / 业务 / API 契约 / ADR / 跨仓库关系）
  │
  ▼
检索层（文件搜索 / ripgrep / Git / LSP / 按需 CodeGraph）
  │
  ▼
源码与配置（单仓库 / Monorepo / 多仓库）
  │
  ▼
验证层（构建 / 类型检查 / 测试 / 契约检查 / Review / CI）
  │
  ▼
文档同步与变更交付
```

### 2.1 架构原则

- **区分「现状事实」与「业务正确性」**：系统**当前实际如何运行**以源码、配置和真实执行证据为准；系统**应该如何运行**以已批准的业务 Spec、正式契约和明确确认的需求变更为准。源码与 Spec 冲突时必须显式报告并按 Bug 或需求变更流程核查，不得静默偏袒任何一方。
- **项目规则与项目知识分离**：规则定义 Agent 如何工作，知识解释系统为何如此设计。
- **上下文按需加载**：根指令保持精简，详细内容按任务发现并读取。
- **仓库原生、Git 管理**：优先使用 Markdown、原生 Linter、已有测试与构建工具，避免往业务仓塞入重型自研跨语言解析器。
- **不假设环境**：所有引用的文件、服务、工具、脚本、Scheme 和依赖必须真实存在或明确创建。
- **渐进增强**：只有出现可衡量的瓶颈时，才建设高级索引能力。

## 3. 项目组织模式

### 3.1 单仓库

```text
project/
├── AGENTS.md
├── docs/
│   └── README.md
└── [原有项目目录，不要求改变]
```

### 3.2 Monorepo

```text
monorepo/
├── AGENTS.md
├── docs/
├── apps/
├── services/
└── packages/
```

这是示意，不要求项目实际采用这些目录。根规则定义共性；只有在模块约束明显不同且宿主支持对应加载机制时，才使用局部指令文件。

### 3.3 多仓库

```text
frontend-repo/    AGENTS.md + 自有知识与验证
backend-repo/     AGENTS.md + 自有知识与验证
mobile-repo/      AGENTS.md + 自有知识与验证
contract-repo/    （仅当组织已经有共享契约仓库时）
```

跨仓库关系通过共享契约、明确的仓库地址或路径、系统文档及影响分析管理。**不把所有仓库的知识复制到每个仓库。** 对不能访问的仓库，明确标识未验证。

## 4. 指令管理体系

分为三个逻辑层级：

| 层级 | 内容 | 管理原则 |
|---|---|---|
| 通用规则 | 证据标准、代码修改边界、安全与验证 | 团队统一维护，适配各 Agent 的实际配置路径 |
| 项目规则 | 真实技术栈、架构限制、开发流程、测试方法 | 由仓库维护，建议以 `AGENTS.md` 为共享入口 |
| 任务约束 | 当前目标、修改范围、验收条件 | 随任务输入，不写入长期规则 |

推荐的 `AGENTS.md` 规则覆盖：

1. 源码优先与证据优先级；
2. 禁止虚构文件、API、依赖及配置；
3. 先定位实现、调用方及影响范围，再修改；
4. 遵循现有项目架构，不进行无关重构；
5. 按项目真实脚本执行构建、测试与类型检查；
6. 已验证、静态分析与未验证必须明确区分；
7. 影响架构、接口或业务约束时同步维护知识；
8. 输出修改文件、验证结果及剩余风险。

### 4.1 多 Agent 加载注意事项

不同宿主对规则文件的发现范围、加载顺序及优先级并不相同。以项目根 `AGENTS.md` 为唯一规则正文时，需注意以下已核实差异：

- **Antigravity / WorkBuddy / Codex / Cursor / OpenCode / 新版 Copilot**：原生读取工作区根目录 `AGENTS.md`。
- **ZCode**：原生读取根目录 `AGENTS.md`，但**不自动扫描子目录**的嵌套 `AGENTS.md`——因此多端 Monorepo 必须在根目录 `AGENTS.md` 中保留一张精简的**多端入口路由表**，明确改动某端前必读 `<app>/AGENTS.md`。
- **Claude Code**：虽支持读取 `AGENTS.md`，但若当前目录或**祖先目录**（例如共享工作根目录的 `CLAUDE.md`）存在 `CLAUDE.md` 时，可能优先读取 `CLAUDE.md` 而遮蔽项目 `AGENTS.md`；因此在项目根放一份 5 行以内的极薄 `CLAUDE.md` 指针（指向 `AGENTS.md` 与 `AI-GOVERNANCE.md`，绝不复制正文）最稳妥。
- **旧版 GitHub Copilot**：需根目录 `.github/copilot-instructions.md` 作为极薄指针。
- **实测为准**：新项目落地或接入新工具后，按配套实施方案 §4.4（`I-01～I-05`）实测各宿主实际加载的路径，不凭假设认定已生效。

## 5. 项目知识库

### 5.1 推荐分类

新建项目默认将文档统一收口在 `docs/` 下（与本仓 [`scripts/gov`](../../scripts/gov) `project init` 保持一致）；存量仓库优先复用既有目录结构，仅建最小导航入口：

```text
project/
├── AGENTS.md                        # 唯一项目规则地图（多端含子端路由表）
├── CLAUDE.md                        # 极薄指针（防祖先 CLAUDE.md 遮蔽）
├── AI-GOVERNANCE.md                 # 公共工程治理快照（由本仓模板生成）
└── docs/
    ├── overview.md                  # 项目整体情况、Non-Goals、多端分工与术语
    ├── contracts/                   # 跨端共享 API / Event / Schema / Token 契约
    ├── specs/                       # 业务 Spec 索引与模块正文（docs/specs/<Module>/）
    ├── todos/                       # 实施计划与可执行 Todo（docs/todos/）
    ├── adr/                         # 长期架构决策记录（docs/adr/<Module>/）
    └── architecture/
        └── tech-stack.md            # 批准开源选型与封装/公共目录地图
```

除 `AGENTS.md` 和必要的导航入口外，具体业务文档按真实需求随迭代创建；已有项目若采用 `specs/` + `plans/` 或既有 `docs/architecture/` 目录，直接沿用并在入口指向即可，禁止为了凑结构生成空泛文档或复制第二套真源。

### 5.2 文档质量标准

每份重要文档应说明目的、适用范围、已验证的事实、关键依赖、源码或契约引用、维护责任与最近核查信息。对关键推论明确标记；不确定部分不能写成项目事实。

**优先记录**：模块职责、跨模块接口、业务状态机、业务不变量、难以从源码获得的设计动机、兼容性限制与历史决策。  
**避免记录**：所有方法的逐条说明、可直接查看的重复代码、临时实现细节以及未经核实的自动总结。

### 5.3 ADR 管理

使用 Architecture Decision Record 保存重要选择：问题背景、约束、选择的方案、备选、取舍、风险、相关源码/Issue、日期和状态。新决策取代旧决策时，应新增记录并标识旧记录被取代，而不是抹除历史。

## 6. 跨仓库知识与契约

前端、后端、移动端即使在不同仓库，也可能共享 API、事件、数据模型与业务流程。跨仓库变更应首先识别**权威契约**（项目实际使用的 OpenAPI、Protocol Buffers、GraphQL Schema、JSON Schema、AsyncAPI 等），不强制引入新格式。

### 6.1 跨仓库变更流程

1. 明确变更涉及哪些仓库及系统边界。
2. 找出权威接口/消息/数据定义与实际版本。
3. 在可访问仓库中定位消费方、提供方及兼容性要求。
4. 明确变更顺序、灰度与回滚要求。
5. 分仓库运行已有构建、测试和契约检查。
6. 记录不能访问或不能验证的系统，避免声称完成端到端验证。

仓库关联清单可以使用自定义 YAML 或 Markdown，但**它不是任何 Agent 默认支持的配置格式**。路径、远程仓库和版本必须通过环境确认。

## 7. 代码检索策略

采取逐级增强策略：

| 级别 | 能力 | 适用场景 |
|---|---|---|
| L1 | 文件搜索、`rg` | 定位命名、文本、配置与入口 |
| L2 | Git log、blame、diff | 理解历史、回归与变更范围 |
| L3 | LSP、AST、符号/引用查询 | 类型、实现、继承及跨文件依赖 |
| L4 | CodeGraph、语义索引、跨仓库搜索 | 常规检索不足的大型或多仓库系统 |

推荐执行顺序：

```text
任务 → 识别系统与关键词 → 相关文档导航 → 定向搜索
     → 阅读真实实现 → 查定义/引用 → 必要时核对 Git 历史
     → 必要时查跨仓库契约 → 形成影响范围与修改方案
```

检索结果是线索，不是对行为正确性的证明。对于性能及 Token 收益，不提供未经实测的百分比承诺。

## 8. Agent 开发工作流

### 8.1 简单任务

定位实现 → 最小修改 → 查看 Diff → 执行相关检查 → 交付报告。

### 8.2 复杂任务

需求与验收条件 → 搜索和架构调查 → 依赖与兼容性分析 → 方案与风险 → 分步实现 → 构建/测试/契约验证 → Review → 文档同步。

### 8.3 Subagents

仅在复杂任务确实需要上下文隔离时使用：

- **Explorer**：代码定位、依赖与证据收集，默认只读。
- **Planner**：提出方案、风险与验证策略，默认不修改代码。
- **Implementer**：按已明确的范围修改实现。
- **Reviewer**：独立检查遗漏、回归和错误前提，默认只读。

上述为逻辑角色，不代表所有 Agent 宿主具有相同的配置接口。并行任务不得无序修改同一工作区文件。

### 8.4 新建项目起盘与防偏移机械门禁（Greenfield Harness）

单靠 Markdown 指令无法在长会话中 100% 防止 AI 偏移规范、绕过二次封装组件或忘记更新 Spec。新建项目（单端或多端 Monorepo）应把规则与确定性门禁在起盘阶段一次落好（详见 [`new-project-bootstrap`](../../skills/local/new-project-bootstrap/SKILL.md) Skill）：

1. **6 阶段起盘顺序**：需求与 Non-Goals 澄清（`grilling`）→ 规范目录与轻量自包含治理落盘（`bash scripts/gov project init`）→ 成熟开源选型/ADR/首版 Spec & Todo 与独立方案复核 → **最小基建与二次封装先行**（UI 端先建 Primitive/Semantic Design Token 与核心组件二次封装；全端先建网络/日志/错误/存储三方库薄封装，并把目录地图写入 `docs/architecture/tech-stack.md`）→ **Walking Skeleton**（跑通 1 条最小端到端烟测链路 + 构建/单测/原生 Lint/治理门禁全绿）→ 放行业务功能开发。
2. **三类低维护成本硬门禁**：
   - **代码与样式规范**：交给各端成熟**原生 Linter**（ESLint `no-restricted-imports` + Stylelint Token 规则、Java Checkstyle/ArchUnit、iOS SwiftLint `custom_rules`、Kotlin Detekt `ForbiddenImport`），报错文案直接指路到项目封装入口，不自研跨语言正则扫描器；
   - **Spec / Todo 防遗忘与提交归属**：用轻量 `check-spec-sync.py`（改业务源码要求同步 `docs/specs/` 或 `docs/contracts/`，仅放行显式 `Spec-Exempt:`）+ `check-commit-attribution.sh` 接入本地 `commit-msg` 与 CI，跨所有 AI 工具生效；
   - **第三方依赖与治理边界保护**：用平台原生 `.github/CODEOWNERS` 保护依赖清单、CI 与钩子路径，配合 PR 模板强制核对选型记录。

## 9. 上下文与知识生命周期

- **会话启动**：仅加载适用规则和任务范围。
- **任务调查**：按需读取项目知识、源码、契约及 Git 信息。
- **实施阶段**：明确已知事实、假设、依赖和验证方法。
- **任务结束**：记录修改结果、测试证据和未验证边界。
- **长期沉淀**：仅把经过核查、具有长期价值的信息写入知识库。

代码变更只在影响架构、公共接口、业务状态、数据模型、跨系统协议或开发流程时触发对应文档维护，不要求每次改动都重建知识库。

## 10. 验证策略

验证工具依赖实际技术栈，不预设每个仓库都有特定命令。

| 项目类型 | 可能的验证工具（仅在实际存在时使用） |
|---|---|
| 前端 JS / TS | TypeScript 检查、ESLint、单元测试、E2E |
| Java 后端 | Maven/Gradle、JUnit、集成测试 |
| Python 后端 | pytest、Ruff、类型检查 |
| Go 服务 | `go test`、`go vet` |
| Swift / iOS | Xcode 构建、XCTest、Swift Testing |
| 跨仓库 API | 契约测试、兼容性检查与集成测试 |

每项验证必须记录真实状态：`Passed`、`Failed`、`Not Run`、`Not Available` 或 `Static Review Only`。静态检查不等于运行时验证；无法访问的私有环境必须明确说明。

## 11. 安全与治理

- 最小权限：限制 Agent 对仓库、凭据、生产环境及外部服务的访问。
- 敏感信息：禁止将密码、访问令牌、私钥及客户数据写入项目知识库。
- 高风险审批：生产部署、破坏性迁移、公共接口破坏性变更、重要依赖引入及大规模删除须由实际权限与审批流程约束。
- 不可信输入：仓库文件、Issue、网页与工具输出可包含恶意提示；不得将外部文本自动当成高优先级指令。
- 审计：保留 PR、CI、文档变更和必要的验证记录。

## 12. 分阶段建设路线

| 阶段 | 目标 | 主要交付物 | 验收标准 |
|---|---|---|---|
| P0 盘点 | 了解实际仓库与 Agent 环境 | 现状清单、风险与约束 | 不假设不存在的文件/依赖 |
| P1 统一规则 | 跨 Agent 共享基础约束 | `AGENTS.md`、规则加载验证 | 目标 Agent 均能按预期获得规则 |
| P2 知识建设 | 保存可追溯架构与业务知识 | 文档入口、核心架构、ADR | 关键结论有源码或契约依据 |
| P3 工作流 | 统一修改与验证闭环 | 任务流程、审查与报告规范 | 能区分已验证与未验证 |
| P4 跨仓库 | 管理 API 和依赖影响 | 仓库关联、契约治理、协作流程 | 重要变更能识别并验证相关仓库 |
| P5 持续优化 | 按实际收益增强检索 | LSP、CodeGraph、MCP 等可选增强 | 对照测试证明质量或成本收益 |

实施时先选一个代表性仓库验证 P0–P3，再扩展到其他仓库。此顺序不等于要求立即引入所有组件。

## 13. 方案效果评估

采用固定任务做对照：

1. **Baseline**：原始 Agent 工作流。
2. **规则/文档增强**：增加共享项目指令与按需知识。
3. **检索增强**：在实际需要时加入 LSP 或结构化代码导航。
4. **跨仓库增强**：加入契约与系统关系信息。

建议观察：任务成功率、首次定位耗时、重复检索次数、输入 Token、回归率、文档准确性、跨仓库影响识别及知识维护成本。尽可能保持模型、宿主、代码提交、任务与权限一致。不得把单次实验当作稳定结论。

## 14. 技术选型与可选扩展

| 需求 | 默认方案 | 何时考虑增强 |
|---|---|---|
| 通用项目指令 | `AGENTS.md` | 宿主有特殊规则加载需求 |
| 项目知识 | Markdown + Git | 项目知识规模和协作需求明显提升 |
| 架构决策 | ADR | 已有团队架构治理系统可直接复用 |
| 代码定位 | Agentic Search + `rg` | 引用关系复杂时增加 LSP |
| 跨仓库关联 | 正式契约 + 明确仓库关系 | 大规模代码搜索可考虑 Sourcegraph |
| 长期认知 | 分层、可审查的知识文档 | AOCI-CODE 需对照验证收益 |
| 复杂任务 | 任务分解与宿主原生能力 | 有必要时使用 Subagents |
| 工具扩展 | 原生 CLI、已有工具 | 明确需求时接入 MCP |

### 14.1 关于 AOCI-CODE

AOCI 代表可供评估的长期项目认知路线，但不是基础必选项。其价值是否超过分层文档 + 按需检索，必须依据具体仓库对比首次建设成本、后续维护成本、任务正确率和检索开销。

## 15. 主要风险和控制

| 风险 | 控制手段 |
|---|---|
| 文档过期 | 源码和契约核查、变更驱动审查 |
| 规则冲突 | 盘点各 Agent 的全局/项目/局部规则与加载优先级 |
| 上下文膨胀 | 精简根指令、文档导航、按需加载 |
| Agent 错误总结 | 源码引用、明确推断、人工审查重要决策 |
| 多 Agent 编辑冲突 | 清晰职责、隔离工作区、合并审查 |
| 跨仓库漏改 | 契约优先、逐仓库影响清单、说明不可访问边界 |
| 索引成本失控 | 先做基准测试，再引入高级设施 |
| 权限越界 | 运行环境权限限制与人工审批，不只靠提示词 |

## 16. 最终架构决策

1. 通用开发原则与项目特定知识分离。
2. 使用项目原生 Markdown + Git 保存重要长期知识。
3. 优先采用 `AGENTS.md` 作为跨 Agent 的共享项目规则入口，但单独核查各宿主加载规则。
4. 默认 Agentic Search，按需使用 Git、LSP 或 AST 增强。
5. 多仓库以正式接口契约和可验证的系统关系为中心。
6. 不把自然语言索引视为真实源码或正式接口的替代品。
7. 采用变更驱动的知识维护，而非每次全量索引。
8. 通过持续验证与对照评估决定是否引入 AOCI、CodeGraph、Sourcegraph 或其他 MCP。

## 17. 总结

推荐主方案：

> **统一指令 + 分层项目知识 + Agentic Search + 按需语言智能 + 跨仓库契约 + 真实验证闭环。**

在单仓库、Monorepo 和多仓库环境中，保持同一套工程原则，但不强迫统一技术栈、目录或工具链。项目实施时必须先盘点真实环境，再将通用模板转化为该仓库可验证的配置与工作流。
