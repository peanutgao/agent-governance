### 关键设计决定

- **单机唯一真源仍是 `~/.codex/AGENTS.md`**，其余工具入口一律软链指过去，不产生第二份内容。
  唯一例外是 WorkBuddy —— 它的用户级规则必须带 frontmatter（`alwaysApply: true`），软链做不到，
  所以是「分发时生成」而非软链。因此它进不了 `LINK_TARGETS`，单独走 `workbuddy_rule_content()`。
- **`--governance` 模式解自应用死锁**：治理仓的提交本身就要描述「AI 归属」这件事，
  默认模式必然拦下。该模式**只跳过 message 披露短语检查**，co-author trailer 与身份检查照常生效
  （有测试 `governance-mode-still-checks-trailer` / `-identity` 钉住这个边界）。
- **checker 改用 bash 内建匹配**（`[[ =~ ]]` + `shopt -s nocasematch` + 逐行 `while read`），
  不再调 `grep`。原因见下。
- **整组快照回滚**替代逐文件 `.bak-*`：`~/.codex/.gov-backup/<ts>/manifest`（`index\tdest\tstate`，
  state ∈ present/absent），回滚时按 manifest 恢复或删除，解决「快照里没有的新增文件回滚不掉」。

### 性能根因（值得记住）

`bash tests/check-commit-attribution.sh` 从 1.3s 退化到 **42.5s**，一次分发 65s。二分定位到根因：
**本机 PATH 上的 `grep` 被解析到 WorkBuddy 的代理 shim**
（`/Applications/WorkBuddy AI.app/Contents/Resources/app.asar.unpacked/cli/vendor/shim/brokered-bin/grep`），
每次调用约 110ms（对比 `/opt/homebrew/bin/grep` 4ms、bash 内建 3ms），而且**出现过漏匹配**
（`--audit-history` 的 17 处违规用流水线跑不出来，直接跑才有）。

**教训：在 WorkBuddy 环境里写脚本，不要假设 `grep` 是 GNU grep。** 能用 bash 内建就用内建。
修复后：单次 checker 850ms → 82ms，归属套件 42.5s → 5.4s，分发 65s → 18.8s。
