- 本文件只描述跨项目共同的工程治理规则。

## 2. 正确性来源

开始任何任务前必须回答：

~~~text
What defines correctness for this task?
~~~

合法的业务真相来源按优先级为：

1. Approved / Active Spec；
2. 明确批准的需求变更；
3. API / Event / Data Contract；
4. Architecture / Design 约束；
5. 项目 AGENTS.md 中的项目规则。

已明确批准的新决定与旧 Spec 冲突时，按需求变更流程同步 Spec 后再实现。

以下内容不能自动定义业务正确性：

- 现有代码；
- 现有测试；
- README；
- 示例代码；
- 历史计划；
- Git 历史；
- AI 推断；
- 行业惯例。

若需决定业务行为而找不到权威来源，将 Truth Source 标记为 undefined 并进入需求澄清。机械改动、样式和其他非业务变更按明确指令与项目规则验收。

- 用户明确要求停止或暂停时，立即停止相关操作，直至用户明确恢复。用户指出错误并给出继续方向时，按新指令修正；不明确的取消意图先澄清。

## 4. 任务分类

每个任务先分类，不得默认所有问题都是代码 Bug：

~~~text
A. New Feature
B. Requirement Change
C. Implementation Bug
D. Missing Requirement
E. Incorrect Requirement
F. Architecture Limitation
G. Data Issue
H. External Dependency Issue
I. Non-behavioral Change
~~~

分类必须写入任务或 PR 记录。实现过程中如果分类发生变化，必须停止当前路径并重新规划。

### 变更分级

分类回答「这是什么性质的任务」，分级回答「要走多重的流程」。两者都要定，级别由改动面决定，不由话题听起来像什么决定。

| 级别 | 判定 | 流程 |
| --- | --- | --- |
| L0 文案/样式/注释/文档 | 只改用户可见文字、类名、注释、说明；不改逻辑、接口、数据、构建配置 | 直接改并同步文案真源；项目适用的静态检查；跳过 Impact Analysis、独立复核、Plan、文档漂移检查；不建决策条目 |
| L1 局部实现 | 单模块行为修正；不改公共接口、数据模型、权限、持久化、编译边界 | Bug 快速路径或直接实现；一次针对性验证 + 局部对抗性复核 |
| L2 契约/架构 | 改接口、数据模型、权限、持久化、分发、安全边界，或跨模块重构 | 完整流程：Spec/ADR → Plan → 独立复核 → 全量门禁 |

- 等级决定默认流程，与本文件的验证要求、§6 前置复核门禁、以及项目 AGENTS.md 的额外要求分别判断，三者取并集。
- 仍不确定时只问一个问题；禁止两个分支都做。
- 动手前写下判定、范围与停止条件三行；范围变化先改这三行。

## 5. 需求变更门禁

改变已批准的产品目标或对外契约才进入 Requirement Change。修复实现以恢复已批准行为仍是 Implementation Bug，纯文案和视觉调整按实际影响分级。以下领域出现已批准目标变化时适用本流程：

- 用户可见行为；
- API；
- Event；
- 状态；
- 权限；
- 金额；
- 业务计算；
- 数据保留；
- 默认策略；
- 通知；
- 状态转换；
- 第三方集成；
- 兼容性行为；
- 文件格式；
- 持久化模型。

处理顺序固定为：

~~~text
Change Proposal
→ 逐条澄清
→ 明确决策
→ 命中前置复核条件时先通过独立方案复核
→ 更新权威 Spec
→ 更新 Design / Contract
→ 重新规划
→ 实现
~~~

未确认的 Change Proposal 不是正式业务真相，不能作为实现依据。

需求尚未澄清、存在未决决策时，禁止直接产出计划文档；必须先以对抗式拷问逐条达成共识，再进入设计与计划编写。

**逐条澄清、一次只问一个是强制执行要求，不是可选参考**：业务逻辑不明确、需求有多个合理方案或进入对抗式拷问时，一次只问一个问题，据上一个答复追问下一问；禁止一次抛出多个问题让用户选择或回答。

每个问题必须附带当前情景、已知信息和 AI 建议；下一问题必须参考并核验用户上一个回答。用户的回答是待核验的输入：与 Spec、代码可验证事实或复现结果冲突时，先指出冲突、依据和建议，不得为顺着用户而静默接受错误前提。

用户对已有方案提出替代方案时，查证新方案依赖的事实和影响，说明证据冲突与业务取舍。用户确认新的业务取舍后，按需求变更流程更新权威文档。

## 6. 需求分流豁免

机械性改动、明显且局部的简单 Bug、纯局部样式调整，可跳过头脑风暴、对抗式拷问、设计冻结与实现计划环节，但仍须自审和执行相称验证。仅当**同时满足**以下条件才可豁免：

1. 改动仅限单一、明确的局部行为或视觉表现；
2. 预期行为有明确依据，修复类任务的直接根因可由代码、测试或复现确定；
3. 不改变公共接口、数据模型、持久化数据、IPC、安全、权限、计费或文件兼容性；
4. 不需要新增依赖、抽象层、配置项或跨模块协调；
5. 不触发本规则或项目规则的前置独立复核。

不符合快速路径时，按任务性质和影响选择诊断、设计或完整变更流程。等级决定默认流程，项目明确要求的验证和独立复核门禁分别判断。L0 运行已有且适用的静态检查，无对应命令时核对改动和引用。全量测试须取得用户明确授权。

### 实现前的独立方案复核

新项目首次确定基础架构，实质性改变模块边界、公共契约、安全、权限、关键状态、持久化数据、迁移或兼容性，以及拟替代或绕开可用现成组件的自研方案，编码前须复核。普通功能按已批准边界实施时继续走对应流程。项目的其他前置复核要求一并执行。

在现有方案或任务记录中提供批准的需求、受影响的边界与调用方、复用候选和最小可行方案。优先由未参与提出或实现该方案的子 Agent 独立查证，也可由满足同一独立条件的人员复核。给出「通过」或「需修订」、依据及至少一个具体反例或失败场景。方案实质变化时复核受影响的决定。缺少独立 reviewer 时记录待审，继续调查和复现，复核通过后修改受门禁的实现。

复核按「方案产出 → 独立 reviewer 对抗性评估 → 主 agent 复核 → 修订方案」循环推进，直到双方对方案达成一致。主 agent 须复核 reviewer 结论，不默认接受；存在分歧时回到方案修订。循环上限 3 轮；仍未收敛即停止，列出分歧点交由用户决策，方案保持待批、不进入实现。

## 7. Bug 和架构问题

Implementation Bug 的处理方式：

~~~text
复现 Expected / Actual
→ 对照 Approved Spec
→ 定位根因和影响面
→ 命中 §6 或项目的前置复核条件时先通过独立复核
→ 最小修复
→ 回归验证
~~~

禁止通过 catch 吞错、条件绕过、延迟、重试、复制另一套逻辑或兜底假数据掩盖根因。

根因不明时，先取得能区分候选原因的复现、运行证据或代码路径，再在直接起因处修改。报告受影响的调用链和能够检验修复的信号。

非显然、间歇性、跨模块或高风险 Bug 先查证真实性、直接根因与受影响的调用方。命中 §6 或项目独立复核门禁时，由符合独立条件的人员或子 Agent 审查，通过后实现；未命中时按实际影响完成诊断与验证。

如果 Spec 本身不正确，重分类为 Incorrect Requirement，按 §5 澄清并确认决策，再更新权威 Spec。

如果正确需求无法由现有架构安全实现，重分类为 Architecture Limitation，先写 Design Proposal 和 Impact Analysis。独立方案复核通过后，更新 ADR、架构及受影响的 Contract，再重新规划和实现。

## 8. 多 Agent 并行实施门禁

默认单 Agent 串行实施；只有**同时**满足以下条件才允许多个子 Agent 并行实现：

1. 需求已冻结（approved spec），且能拆成边界清晰、相互独立的子任务（无共享可变状态、无顺序依赖、无重叠改动区）；
2. 每个子任务有明确的验收标准与交付物（涉及文件 / 接口清单）；
3. 拆分方案（子任务划分、接口契约、执行顺序）先经用户确认，与设计冻结同一门禁，不得自行拆分或临时加派；
4. 并行子任务可能触碰同一模块 / 文件 / 接口时，用 git worktree 或明确分区隔离，避免互相覆盖。

并行实施期间与完成后必须：

- 每个子 Agent 交付前自验（typecheck / lint / 相关测试）；
- 全部完成后重新 review 合并后的代码，检查集成点、接口对齐、重复或冲突，不得跳过；
- 合并后跑一次跨模块集成验证（相关测试 + build）确认无回归；
- 任一子任务需要改动已批准 Spec / 接口时，暂停相关实现并回到 §5。澄清后按 §6 判断是否复核变更的决定，再更新权威文档和重新规划。

不满足上述条件时一律单 Agent 串行执行，不得为「进度快」强行拆分。

## 10. 先更新知识再实现

实现前按受影响范围更新权威文档：

- 已批准的业务行为新增或变化时，更新对应 Spec，缺失时按现有目录约定创建。
- 架构边界变化时，更新当前架构文档和对应 ADR，缺失时按现有目录约定创建。
- 公共契约变化时，更新受影响的 API / Event / Data Contract。

不要为了让测试变绿而修改测试期望。权威需求正式变化时同步测试；有证据表明原测试违背现行 Spec 时，可以按 Spec 修正预期。

## 12. 代码质量

实现类变更完成前必须确认：

- 没有未引用的 import、变量、函数、分支、配置项或文件；
- 没有重复三次仍未抽取的逻辑；
- 没有为单一实现新增抽象层、工厂、策略、注册表或未来扩展点；
- 没有无证据的判空、catch 兜底、重试、降级或 fallback；
- 没有空函数、桩实现、未接通路径或 TODO 未实现占位；
- 没有明知项目已有实现仍重写一套；
- 新代码遵守本项目的分层和依赖方向；
- 有加载态时提交类入口不能重复触发；
- 没有为极低概率并发路径添加无证据的锁、定时器或状态机。

## 13. 依赖准入

引入任何第三方库前必须**同时**满足：

1. GitHub stars > 1k 或 npm 周下载 > 50k；
2. 最近 12 个月有 release；
3. TypeScript 类型完整；
4. 没有可被 100 行以内手写替代的更轻量方案。

候选库先列出多方案对比（成熟度、维护状态、体积、与现有依赖的兼容），经用户确认后再引入。禁止引入自包装 HTTP client、自写事件总线、自写 DI 容器等与「优先用成熟开源库」相悖的轮子；项目另有更严依赖政策的，以项目 AGENTS.md 为准。

## 14. 数据、安全和不可逆操作

以下内容不得出现在对话、日志、Issue、PR 或提示词中：

- 生产密钥、API key、token、证书、私钥、数据库口令；
- 客户手机号、邮箱、地址、身份信息；
- 真实订单、支付流水和对账明细。

生产环境：

- 可在授权范围内读取非敏感日志、容器状态和配置；
- 不得执行 UPDATE、DELETE、迁移、部署、重启或生产配置写入；
- 这些操作只输出方案和命令，交由人执行。

访问或操作任何数据库或钥匙串前，必须取得用户对本次具体操作的明确授权。读取、查询、刷新、写入、删除、迁移、备份、恢复、临时或测试实例，以及会间接访问它们的命令均适用；替换可能影响既有钥匙串授权的组件也须单独授权。通用的实现、修复或验证授权不覆盖这些操作。

未经明确授权不得执行：

- force push；
- 删除远端分支或 tag；
- 重写已推送历史；
- 清理或重置用户工作树；
- 覆盖无法恢复的数据。

## 15. 禁改区与治理边界

某些路径的改动一旦出错代价不可逆（资金、权限、数据迁移、发布与供应链、安全边界、业务真相），由各项目定义为**禁改区**，AI 不得直接落盘：

- 按项目规则识别受保护路径和审批人。`.github/CODEOWNERS` 提供路径归属，禁改范围与审批方式由项目规则定义。
- 触碰禁改区时，只产出改动方案。项目明确允许时，可在独立分支或草稿 PR 准备变更，获对应 owner 批准后才合并或推主干。
- 例外必须留痕，口头授权不算：
  ~~~text
  Governance-Exception: <区域> | approved-by=@<owner> | reason=<一句话>
  ~~~
- 拿不准某路径是否属禁改区时，先问，不要自行判定为普通区。
- 放宽禁改区门禁的改动（CODEOWNERS、CI、发布脚本、钩子）同属禁改区，不得由 AI 自行合入。

**收窄：新建 spec 不要求 trailer。** 在 `specs/` / `**/spec/` 下新建此前不存在的 spec 文件，且不改动任何已有 `approved` / `active` 条目时，只需 owner 在当次会话中确认内容即可落盘；为该新 spec 所做的索引与 traceability 登记同属此列。原本没有业务真相存在，也就不存在被静默改写的风险。**修改**既有 spec（改写 Business Rules / Acceptance Criteria、变更状态机、标记 deprecated、或新 spec 覆盖既有规则）不适用本收窄。

## 16. Git 提交作者归属

项目禁止 AI、模型、Agent 或 Bot 作为 Git commit 的 author、committer 或 co-author 出现。

新提交禁止出现以下 trailer 或等价合作作者声明：

~~~text
Co-Authored-By:
Co-authored-by:
Co-Author:
Coauthor:
~~~

身份与提交消息的可执行拦截清单以项目接入的 `check-commit-attribution.sh --print-policy` 为准。

- 未经用户明确要求，AI 不得执行 `git commit`、`git commit --amend` 或自动提交任何代码、规则或文档；修改完成、验证通过或用户说“完成”都不等于获得提交授权。
- Git commit 使用人类开发者的 author 和 committer 身份。
- 项目交付物和协作记录不得披露 AI 参与、模型、供应商、Agent、Bot、生成归属、提示词或类似自动化身份信息；范围包括 commit metadata/message、代码注释、文档、Spec、ADR、PR、Issue、审查记录、任务总结和日志。
- 历史提交不重写；只阻止新的 AI 信息披露，不把“未披露”误写成“未使用”。

~~~text
Governance-Exception: ...
~~~

是 owner 审批记录，不是作者归属声明，可以继续使用。

检查新提交时只检查当前 PR 或 push 新增的 commit，不因历史旧记录失败。

## 17. 测试、审查和收尾

完成前必须：

- 运行与改动相关的真实验证命令；
- 不使用“应该通过”“已验证”等替代真实输出；
- 自审完整 diff；
- 清理调试代码、临时日志和无效注释；
- 检查错误处理、安全边界和相关文档；
- 搜索旧参数、旧状态、旧 API、旧 Event 和旧术语；
- 处理或明确记录每个残留引用；
- 对高风险、跨模块、权限、安全、数据和非显然 Bug 取得独立 reviewer 审查。

完整流程结束时输出以下信息，简单 Bug 按 §20 简报，L0 只说明改动和适用验证。

~~~text
Classification:
Truth Source:
Changes:
Spec / Design / Contract Updates:
Tests:
Verification:
Remaining Risks / Follow-ups:
~~~

并逐项 Reconciliation：

~~~text
Spec:
Design:
Contract:
Code:
Tests:
~~~

任一项存在未解决问题，不得宣称任务完成。

## 18. Spec 与 ADR 目录约定

- 通用项目默认使用 `specs/README.md` 作为业务 Spec 索引，使用 `specs/<Module>/` 按模块存放当前业务 Spec 文件。
- 通用项目默认使用 `docs/adr/README.md` 作为 ADR 索引，使用 `docs/adr/<Module>/` 按模块或领域存放 ADR 文件。
- 索引只负责导航、状态和简短范围说明；正文放对应模块目录，不在根目录散放业务文件。
- Spec 记录已确认的当前业务行为、边界、失败行为和验收条件；ADR 记录需要长期保留的架构或合同决策。Plan、brainstorm、审计记录和历史提案不能替代它们。
- 新增或修改业务行为时更新对应模块 Spec；新增或修改架构/合同决策时更新对应模块 ADR 和索引。恢复已有 Spec 行为的简单 Bug 不新建 Spec；普通实现不默认新建 ADR。
- 文档是否提交到 Git 是项目级发布策略；项目可以声明 Specs/ADR/Plan/brainstorm 仅在本机维护，并用 `.gitignore` 防止新文档进入仓库。
- 项目已采用等价的其他目录时，遵循项目入口并保持“索引 + 模块目录 + 模块文件”的组织方式，不复制第二套文档真源。

## 19. 本机与运行环境

- 不自行启动、重启或停止长期运行的服务（dev server、后端、数据库、Redis、nginx、消息队列等）。需要服务在跑才能验证时，把命令交给用户执行。
- 例外只限一次性验证用的临时进程：先说明、端口不冲突、用完立即清理。
- 不把开发机当生产环境：不安装开机自启或常驻代理（LaunchAgent、systemd unit、常驻 crontab），不改系统级配置。
- 造测试数据前先写清清理方案；无法清理的数据不写入开发库或共享库，也不留在仓库里。


## 20. Bug 快速路径

明显且局部、根因明确、未改变公共接口 / 数据模型 / 权限 / 持久化 / 编译边界，且符合 §6 前置复核豁免条件的 Implementation Bug 可走快速路径。

- 可以读取相关测试，但不要求修改前先运行并通过 baseline tests。
- 修改前先闭合受影响的局部执行链，证明直接根因；修改必须落在根因边界，不得只掩盖表面症状。
- 直接进行最小实现修改，然后执行一次最直接的针对性验证和一次局部对抗性复核。
- 没有合适测试接缝时，不以新增回归测试阻塞修复。
- 未改变编译边界时，不默认完整构建、启动项目或运行端到端流程。
- 只有非显然、间歇性、跨模块或高风险 Bug 才进入完整调试 / 根因复核流程。
- 快速路径完成后只报告根因、改动、选定验证和剩余风险，不进入完整 Impact Analysis / Plan。

## 21. 共享工作树与并发验证

- 多个窗口共享同一项目或工作树时，普通修复窗口只做自己的局部验证，不自动触发共享项目的完整 build / test / run。
- 完整项目验证只有在用户明确要求，或项目规则 / 风险等级明确要求时才运行。
- 对同一工作树可能重叠的 build、test 或 run，统一使用同一个项目级验证锁，所有入口都须在启动前原子获取；取不到就标记 `deferred`。锁仍被持有时不得接管。使用锁目录时，必须确认记录的持有进程已退出且未被复用才能清理；仅经过一段时间不构成依据。命令结束时释放自己的锁。
- 不得根据当前窗口完成状态推断其他窗口已完成；最终完整验证由用户明确触发，或由项目规则明确触发。
- `deferred` 表示验证尚未执行，不是通过；验证后工作树又发生源码或配置变化时，原结果不再自动适用。

## 22. 系统性对抗性复核

- 所有实现类改动在宣称完成前必须进行系统性、对抗性的复核；复核不是“测试通过”的同义词，也不自动要求完整构建或全量测试。
- 复核必须主动尝试推翻当前结论：检查根因是否只是症状、是否存在旁路或相邻分支、边界 / 失败 / 重入 / 并发路径是否仍有问题、改动是否引入回归或扩大范围，以及验证证据是否真的支持结论。
- 简单局部 Bug 做受影响调用链、状态 / 数据流、相邻条件和至少一个最可能反例的局部复核；非显然、跨模块或高风险改动扩大复核范围。
- 复核发现根因、正确性或范围仍不成立时，不得宣称完成；回到需求澄清、诊断、设计或实现阶段。

## 23. 实现约束

- 只实现已经明确的目标，保持最小且连贯的改动。
- 写代码前先搜索项目已有的组件、Service、工具、Schema 和相似实现。新增、替换或自研可复用能力时，在现有任务记录写明候选路径、能覆盖的要求、关键缺口和采用理由。
- 不要为了让测试变绿而改变需求或 Spec。
- 不做未被要求的重构、依赖升级、格式化或清理。
- 不保留空壳实现、调试输出或“以后再做”的未接通路径。
- 发现与当前目标无关的问题，记录后不要顺手扩大范围；安全、权限和数据正确性问题除外，应明确报告。
